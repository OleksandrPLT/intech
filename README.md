# intech.org.ua

Сайт веб-розробника (Полтава, Україна; компанія в процесі реєстрації
також в Естонії), побудований на [Astro](https://astro.build):
розробка сайтів, CRM-системи, кастомні проекти, корпоративний VPN,
налаштування серверів, редизайн сайтів, корпоративна пошта/Workspace,
Telegram-боти. Три мови на маркетинговій частині: українська (`/`),
англійська (`/en/`), естонська (`/et/`).

Сайт має дві частини:

- **Маркетингова** — головна, послуги, портфоліо, новини, про мене,
  контакти (з формою заявки — див. нижче). Контент (послуги, новини,
  портфоліо, контактні дані) редагується з кабінету — жодних правок коду
  для звичайних оновлень. Про мене і 404 лишились статичними
  (prerendered), решта — SSR, бо читає базу на кожен запит.
- **`/app`** (він же `admin.intech.org.ua` — див. нижче) — динамічний
  кабінет: клієнти бачать свої проекти й ведуть тікети, ви керуєте
  клієнтами/проектами/задачами/тікетами, внутрішньою CRM (ліди) і
  контентом сайту, команда бачить призначені їй задачі.

## Структура проекту

```
src/
  components/     # Header, Footer, Logo, ServiceCard, ServiceIcon, TechStack,
                  # PortfolioCard, TicketThread, CustomFieldsForm/View
  layouts/        # BaseLayout (маркетинг), AppLayout (кабінет)
  i18n/           # словники (ui.ts) та хелпери локалізації (utils.ts)
  data/           # services.ts, techStack.ts, portfolio.ts
  db/             # schema.ts (Drizzle), client.ts (з'єднання з SQLite)
  lib/            # auth.ts, session.ts, tickets.ts (контроль доступу),
                  # customFields.ts, ticketCategories.ts, ticketNumber.ts,
                  # ticketMessages.ts, uploads.ts, apiKeys.ts, labels.ts
  middleware.ts   # захист /app/* за роллю (admin / staff / client)
  pages/
    (маркетинг)   # українські сторінки в корені, англійські — під /en/
    login.astro
    app/
      admin/      # дашборд, клієнти (профіль + власні поля), проекти
                  # (+ задачі, + API-ключі), CRM/ліди, тікети, налаштування полів
      staff/      # задачі, призначені члену команди
      client/     # мої проекти (+ read-only задачі), тікети
    api/
      admin/*, tickets/*, staff/*, attachments/*   # форми кабінету (cookie-сесія)
      v1/tickets/*                                 # зовнішнє API (Bearer-ключ)
  styles/         # global.css — кольори, типографіка, компоненти форм/таблиць
scripts/
  create-admin.mjs  # створення акаунта: admin / staff / client
deploy/
  nginx.conf.example      # реверс-проксі до Node-процесу
  intech.service.example  # systemd unit, щоб сервер жив після перезавантаження
data/
  app.db          # SQLite (поза git)
  uploads/        # файли, прикріплені до тікетів (поза git)
```

Кожна послуга описана один раз у `src/data/services.ts` (uk + en + et) —
картки на головній, сторінка `/services` і сторінки `/services/[slug]`
рендерять той самий контент.

### Мови

`uk` (без префікса), `en` (`/en/...`), `et` (`/et/...`) — керує все
`src/i18n/ui.ts` (`languages`, `defaultLang`) та `src/i18n/utils.ts`
(`localizePath`/`localeUrl`, вже розраховані на будь-яку кількість мов,
не лише дві). Щоб додати ще одну мову: додати її в `languages`, додати
блок перекладу в `ui.ts`, додати `<lang>` до кожного об'єкта в
`services.ts`/`portfolio.ts`/`techStack.ts`, і продублювати сторінки з
`src/pages/en/` у `src/pages/<lang>/`. Естонський переклад — робочий,
але писаний не носієм мови: перед тим, як показувати сайт реальним
естонським клієнтам, варто дати native speaker-у звірити копірайтинг
(особливо `about.p2` і опис компанії).

### Форма заявки на сайті

`/contact` (усіма трьома мовами) має форму без логіну — заявка одразу
падає в CRM як новий лід (`stage: 'new'`, `source: 'Сайт (форма
заявки)'`), видно на `/app/admin/leads`. Захист від ботів — honeypot-
поле (`src/pages/api/public/leads.ts`): бот, який заповнює приховане
поле `website`, отримує звичайний "успіх", але запис не створюється.

## Кабінет / CRM — як це працює

Бічна панель адмінки згрупована по секціях (CRM, Підтримка, Контент,
Налаштування — `adminNav` в `AppLayout.astro`, кожен пункт масив
`{group, items}`), а не один довгий список — секція без назви (`group:
null`) лишається над усіма заголовками (зараз там тільки Дашборд).

Клієнти **не реєструються самі** — акаунт створюєте ви:

```bash
# перший адмін-акаунт (ви)
node scripts/create-admin.mjs --email you@intech.org.ua --name "Ваше Ім'я" --password "..."

# акаунт клієнта (або через форму на /app/admin/clients, коли вже увійшли)
node scripts/create-admin.mjs --email client@example.com --name "Ім'я клієнта" --password "..." --role client
```

Далі: `/login` → адмін потрапляє в `/app/admin` (клієнти, проекти,
CRM-ліди, усі тікети), клієнт — у `/app/client` (свої проекти зі
статусом і статусом оплати, свої тікети). Middleware (`src/middleware.ts`)
не пускає клієнта на `/app/admin/*` і будь-кого неавторизованого — на
`/app/*` взагалі. Кожен запит до чужого тікета/проекту (навіть по
прямому посиланню) перевіряється в `src/lib/tickets.ts` і повертає
редирект, а не дані.

**База даних** — SQLite-файл (`data/app.db`, поза git). Для соло-бізнесу
такого масштабу окремий сервер БД не потрібен: один файл, просте
резервне копіювання (`cp data/app.db backup/`), нуль додаткових
сервісів на сервері. Якщо колись переростете — Drizzle ORM робить
перехід на PostgreSQL відносно простим (схема в `src/db/schema.ts`
майже не зміниться).

### Власні поля (custom fields)

`/app/admin/settings/fields` — додаєте поле (назва, тип: текст /
багаторядковий текст / число / дата / список / так-Ні, обов'язкове чи
ні) для ліда, проекту або профілю клієнта — і воно одразу з'являється у
відповідній формі та зберігається без правок коду. Механізм —
`customFieldDefs` + `customFieldValues` у схемі, рендер — компоненти
`CustomFieldsForm`/`CustomFieldsView`, логіка — `src/lib/customFields.ts`.

### Тікети: тематики, номери, вкладення, внутрішні нотатки

Клієнт при створенні тікета обирає тематику (WEB, CRM, VPN, SRV, MAIL,
BOT, DEV, RED, GEN — `src/lib/ticketCategories.ts`), і тікет отримує
номер на кшталт `VPN#00001` — власна послідовність на кожну тематику
(`src/lib/ticketNumber.ts`). До будь-якого повідомлення можна
прикріпити файл (до 10 МБ, зберігається в `data/uploads/<ticketId>/`,
віддається лише тому, хто має доступ до тікета — `/api/attachments/[id]`).
Адмін може лишити **внутрішню нотатку** (чекбокс "клієнт не бачить") —
вона відфільтровується на рівні запиту до бази (`src/lib/ticketMessages.ts`),
а не просто прихована стилями, тож клієнтський API теж її ніколи не поверне.

Коли клієнт створює тікет або відповідає в ньому, **кожен** admin/staff
акаунт отримує власний email (не спільна скринька) — `src/pages/api/tickets.ts`
і `.../tickets/[id]/reply.ts` через `sendMail()`.

### Вкладки тікета: Погодження, Історія змін, Лист клієнту

Тікет (сторінка й модалка на `/app/admin/tickets`) поділений на вкладки —
чиста CSS-реалізація (radio-input техніка), не JS: фрагмент тікета
вставляється в модалку через `innerHTML`, де вбудований `<script>` ніколи
не виконається, тож перемикання вкладок не може залежати від JS
(`TicketDetailContent.astro`, стилі — плоскі класи в `global.css`, не
scoped `<style>` компонента — той теж не переживає innerHTML-вставку).

- **Погодження** — будь-яка сторона тікета може запросити підтвердження
  ("Прошу підтвердити рахунок на 200$"), інша — погодити чи відхилити з
  коментарем (`ticketApprovals`, `/api/tickets/[id]/approvals`,
  `/api/approvals/[id]/respond`).
- **Історія змін** — аудит-лог: зміни статусу, запити/рішення по
  погодженню, надіслані листи клієнту (`ticketEvents`, `src/lib/ticketApprovals.ts`).
  Пишеться автоматично, не потребує окремих дій.
- **Лист клієнту** (тільки адмін) — довільний email напряму клієнту
  проекту (не через тред тікета) — `/api/tickets/[id]/email-client.ts`,
  шаблон `directMessageEmailTemplate` у `emailTemplates.ts`. Результат
  (надіслано / збережено у файл / помилка) одразу видно і в самій
  вкладці, і в "Історія змін".

### Маска телефону

Поле "Телефон" у профілі клієнта (`ClientProfileFields.astro`)
форматується на льоту в `+380 XX XXX XX XX`, хай що саме ввели —
з нулем, з кодом країни чи без.

### Фінанси — головна книга

`/app/admin/finance` — окрема сторінка в сайдбарі, головна книга по всіх
проектах разом: кожен запис — дохід або витрата (`projectPayments.type`),
сума, валюта (UAH/USD/EUR), дата, нотатка, опційна квитанція (файл через
той самий механізм, що й "Файли проекту"). Зверху — баланс по кожній
валюті (дохід мінус витрата), з розбивкою під ним. Фільтри за проектом і
типом; форма додавання — з випадаючим списком проекту (той самий insert,
що й з проекту, — спільна логіка в `src/lib/payments.ts`).

Той самий журнал лишається й на самому проекті — `/app/admin/projects/[id]`
→ вкладка "Фінанси" — зі своїм балансом і швидкою формою додавання (там
проект вже відомий з URL, тож форма без селекта), плюс посилання "Усі
фінанси →" на центральну сторінку.

Для кожного **доходу** — посилання "Квитанція": друкований HTML-документ
(`/app/admin/projects/[id]/receipt?payment=…`) з реальним лого (не просто
текст — той самий двоколірний "курсор", що й в основному бренд-знаку,
явними hex-кольорами, бо документ форсує білий фон незалежно від теми
сайту), реквізитами клієнта (назва компанії/юр. адреса/ЄДРПОУ з профілю
клієнта), сайтом проекту, номером `RCT-{projectId}-{paymentId}` і кнопкою
"Друкувати / Зберегти як PDF" (`window.print()` — без додаткових
залежностей для генерації PDF). Витрати квитанції не мають (нема кого
рахунком виставляти).

При додаванні доходу на сторінці проекту можна позначити галочками, які
задачі він покриває (`projectPayments.taskIds`) — вони підуть окремими
рядками в "За що оплата" на квитанції замість загального опису.

### Рахунки на оплату

Окрема від "Фінансів" сутність — `invoices`, вкладка "Рахунки на оплату"
на сторінці проекту. Рахунок виставляється ДО того, як гроші отримано
(на відміну від `projectPayments`, куди запис додається вже за фактом
оплати): сума, валюта, опис, дата рахунку, термін оплати. Статус
(Не оплачено / Оплачено / Прострочено / Скасовано) редагується прямо в
списку — `<select>`, що сабмітить форму по `onchange`
(`/api/admin/invoices/[id]/status`). Оплата рахунку не створює запис у
Фінансах автоматично — це свідомо окрема дія (виставити рахунок і
зафіксувати фактичний платіж/квитанцію — різні кроки). Друкований
документ — `/app/admin/projects/[id]/invoice?bill=…`, той самий
візуальний шаблон, що й квитанція, але подається як "Рахунок на оплату" з
полем "До сплати" й видимим статусом.

### Договір на 3 мови/юрисдикції

`/app/admin/projects/[id]/contract` — генерація договору про надання
послуг без збереження в базі (документ формується на льоту з
query-параметрів, тож "історії" немає — кожне відкриття це просто новий
рендер). Три версії — це не 3 мови на вибір для однієї версії, а **3
мова = 3 юрисдикція**: `uk` → договір українською під законодавство
України, `et` → leping естонською під Eesti õigus, `en` → generic
Service Agreement англійською для решти країн. Версія підбирається
автоматично за країною клієнта (`UA`→uk, `EE`→et, інше→en), але
перемикається вручну.

Форма нагорі (`<details>`, чиста GET-форма — жодного JS, дані просто в
query string) дозволяє відредагувати номер договору, дату, місце,
реквізити Виконавця й Замовника (підставляються з профілю клієнта —
компанія/адреса/ЄДРПОУ/email — але лишаються редагованими прямо тут,
не тільки в CRM), предмет договору і суму — і одразу перерендерити
документ. Текст шаблонів — `src/lib/contractTemplates.ts` (9 розділів:
предмет, оплата, права/обов'язки, відповідальність, конфіденційність,
форс-мажор, строк дії, застосовне право, прикінцеві положення +
підписи). **Це типовий шаблон, не юридична консультація** — перед тим,
як підписувати ним реальні угоди, варто дати перевірити юристу в кожній
юрисдикції (те саме застереження, що й для естонського тексту сайту).

### Контакти проекту (платник)

`/app/admin/projects/[id]` → блок "Контакти", перемикач Фізична/Юридична
особа (`projects.contactType` + окремі поля — `src/pages/api/admin/projects/[id]/contact.ts`).
Це те, кого реально писати платником на рахунку/квитанції/договорі — не
плутати з профілем клієнтського акаунту (`users.*`): акаунтом може
керувати менеджер, а платник — інша юридична особа. Резолвер
`src/lib/payerInfo.ts` (`resolvePayer`) вибирає ці дані, якщо заповнені,
і падає назад на профіль клієнта, якщо ні — використовується всіма
трьома документами однаково.

### Чиста генерація PDF

Кнопка "Завантажити PDF" на квитанції/рахунку/договорі віддає справжній
PDF-файл (Puppeteer, `src/lib/pdf.ts`), а не покладається на діалог
друку браузера — той тягнув у роздрук темну адмінку разом з документом.
Технічно: кожен з трьох документів має `?bare=1` режим — окрема гілка
рендеру БЕЗ `<AppLayout>` узагалі (власний `<html><head>`, жодного
sidebar у DOM), а не просто `@media print { display: none }` поверх
звичайної сторінки. `/api/admin/projects/[id]/{receipt,invoice,contract}-pdf`
відкривають цю `?bare=1`-сторінку headless-браузером (той самий
запущений сервер, той самий cookie сесії) і зберігають результат як
PDF. Спільна карткова розмітка — `ReceiptCard.astro`/`InvoiceCard.astro`/`ContractCard.astro`,
використовується і в звичайному перегляді (усередині `AppLayout`), і в
`bare`-режимі, тож обидва рендери гарантовано не розходяться.

### Профіль клієнта

`/app/admin/clients` (форма створення) і `/app/admin/clients/[id]`
(профіль) мають, крім кастомних полів, набір фіксованих: телефон,
назва компанії, юридична адреса, ЄДРПОУ/РНОКПП, країна (повний список
у `src/lib/countries.ts`), мова спілкування, і **приватні нотатки
адміна** — останнє поле ніколи не рендериться на жодній
клієнтській сторінці (клієнтського профілю взагалі не існує — тільки
дашборд проектів), тож витоку немає в принципі, не просто "приховано
стилями".

### Пошта (welcome-лист і сповіщення)

`src/lib/mailer.ts` (`nodemailer`) — надсилає HTML-листи через SMTP,
заданий у `.env` (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`,
`SMTP_SECURE`, `SMTP_FROM`). Поки жодного `SMTP_*` не задано, `sendMail()`
нічого не ламає — просто пише лист у `data/emails/<час>-<кому>.html`
замість відправки, щоб можна було відкрити файл у браузері й побачити
точно те, що піде клієнту, ще до підключення реальної поштової скриньки.
Шаблони — `src/lib/emailTemplates.ts` (welcome-лист новому клієнту з
логіном/паролем, сповіщення про новий тікет). Статус SMTP і кнопка
"Надіслати тестовий лист" — на `/app/admin/settings/site`.

### Задачі та команда

Роль `staff` — акаунт члена команди (без доступу до CRM/клієнтів, лише
свої задачі на `/app/staff`). Ви створюєте задачі всередині проекту
(`/app/admin/projects/[id]`) і призначаєте їх на себе чи на когось з
команди; клієнт бачить список задач свого проекту як read-only чекліст
прогресу (без імен виконавців).

```bash
node scripts/create-admin.mjs --email dev@example.com --name "Ім'я" --password "..." --role staff
```

### Зовнішнє API (інтеграція в клієнтські проекти)

Створюєте API-ключ або на сторінці конкретного проекту
(`/app/admin/projects/[id]`), або централізовано на
`/app/admin/api-keys` (видно всі ключі з усіх проектів в одному місці —
зручно, коли клієнтів багато). Кожен ключ прив'язаний саме до одного
проекту (найменша можлива зона довіри — витік ключа відкриває тікети
лише одного проекту, не всю CRM). Ключ показується один раз одразу
після створення.

```bash
# створити тікет із клієнтського сайту
curl -X POST https://intech.org.ua/api/v1/tickets \
  -H "Authorization: Bearer itk_live_…" \
  -H "Content-Type: application/json" \
  -d '{"subject":"Заявка з форми","body":"Текст звернення","category":"WEB"}'

# список тікетів проекту
curl https://intech.org.ua/api/v1/tickets -H "Authorization: Bearer itk_live_…"

# одна заявка з публічними повідомленнями (внутрішні нотатки не повертаються)
curl https://intech.org.ua/api/v1/tickets/3 -H "Authorization: Bearer itk_live_…"

# додати коментар до заявки
curl -X POST https://intech.org.ua/api/v1/tickets/3/messages \
  -H "Authorization: Bearer itk_live_…" -H "Content-Type: application/json" \
  -d '{"body":"Уточнення від клієнта"}'
```

### Проект як хаб: файли, ревізії, доступи

`/app/admin/projects/[id]` збирає все по проекту в одному місці —
відкрив проект і одразу бачиш:

- **Тікети проекту** — та сама таблиця, що й на `/app/admin/tickets`,
  але відфільтрована по цьому проекту (`WHERE project_id = …`).
- **Файли проекту** — спільна файлова зона (окремо від вкладень до
  тікетів): і адмін, і клієнт можуть завантажити файл прямо на
  дашборді (`projectFiles` у схемі, `/api/project-files`, віддача —
  `/api/project-files/[id].ts`, перевірка доступу — той самий
  `canAccessProject()`, що й для тікетів).
- **Ревізії — стрічка на затвердження**: адмін публікує версію (назва,
  опис, опційно файл), клієнт бачить її на своєму дашборді і тисне
  **"Затвердити"** або **"Потрібні правки…"** з коментарем
  (`projectRevisions`, `/api/admin/projects/[id]/revisions`,
  `/api/revisions/[id]/respond`).
- **Доступи (credentials vault)** — логіни/паролі хостингу, реєстратора,
  CMS тощо, лише для адміна. Шифруються AES-256-GCM
  (`src/lib/crypto.ts`), а не хешуються — їх треба вміти прочитати
  назад. Ключ шифрування — `CREDENTIALS_ENCRYPTION_KEY` в `.env`, або,
  якщо не задано, автогенерується один раз у `data/.encryption-key`
  (права `0600`, поза git). **Загубите цей файл без резервної копії —
  збережені паролі відновити буде неможливо** — так і задумано,
  справжнє шифрування, не обфускація. На проді варто явно задати
  `CREDENTIALS_ENCRYPTION_KEY` і зберегти його окремо від бекапу бази.
  Пароль у списку показується замаскованим, кнопка "Показати" підвантажує
  розшифроване значення через окремий запит (`/api/admin/credentials/[id]/reveal`),
  а не одразу в HTML сторінки.

### Тікети як модальне вікно

На `/app/admin/tickets` клік по рядку (не лише по темі) відкриває тікет у
компактному модальному вікні (`<dialog>`) — без переходу зі списку.
Джерело — той самий маршрут `/app/admin/tickets/[id]`, викликаний з
`?partial=1`: повертає лише вміст тікета (без `AppLayout`), який JS
вставляє в модалку через `fetch()`. Спільна розмітка для сторінки й
модалки — `TicketDetailContent.astro`. Посилання лишається справжнім
`<a href>`, тож без JS чи по Ctrl+клік відкриття в новій вкладці й далі
працює — модалка лише прогресивне покращення. Відповідь/зміна статусу
всередині модалки — звичайна відправка форми (веде на повну сторінку
тікета після збереження).

### Компактна адмінка

Основні "рамкові" відступи (`.app-main`, `.app-sidebar`, `.app-header`,
`.data-table`, `.field`, `.ticket-thread`) звужені в `global.css` — це
одразу впливає на всі сторінки кабінету. Поверх цього по всіх файлах
`src/pages/app/**` звужені найбільші inline-відступи (`padding`, `gap`,
`margin-bottom`, розмір заголовків) до єдиної тіснішої шкали.

### Мій профіль

`/app/settings/profile` — доступно будь-якій ролі (адмін/команда/клієнт):
змінити своє ім'я, email і пароль. Зміна вимагає ввести поточний
пароль (перевіряється через `verifyPassword`) — навіть маючи активну
сесію, не можна тихцем підмінити email/пароль на чужому/спільному
пристрої без підтвердження. Посилання — внизу бічної панелі, під
перемикачем теми.

## Адмін-субдомен

`admin.intech.org.ua` — той самий кабінет (`/app`), просто на іншому
хостнеймі: `src/middleware.ts` шле голий `/` на `admin.`-хості на `/app`,
все глибше (`/app/admin/...`, `/login`, `/api/...`) і так уже працює з
будь-якого хостнейма, спрямованого на цей самий Node-процес — переносити
нічого не довелось. `intech.org.ua/app/...` теж і далі працює (не
видалено).

- **Локально**: `http://admin.localhost:4321` — працює одразу, без
  правок `/etc/hosts` (браузери резолвлять `*.localhost` у `127.0.0.1`
  самі).
- **Прод**: другий `server_name admin.intech.org.ua` у
  `deploy/nginx.conf.example`, той самий upstream. Додайте DNS-запис на
  субдомен і випустіть сертифікат з трьома `-d` (приклад — у коментарі
  вгорі файлу конфігурації).

## CMS — контент без правок коду

Новини, портфоліо, послуги та контактні дані (`site_settings`) живуть у
базі, редагуються з `/app/admin/content/*` і `/app/admin/settings/site`
(та сама роль/захист, що й решта адмінки). `src/data/{news,portfolio,
services}.ts` тепер не масиви, а функції-запити до бази (`getNews()`,
`getPortfolio()`, `getServices()`) — типи для компонентів лишились
тими самими.

Перше налаштування (переносить те, що раніше лежало в коді, у базу,
нічого не втрачаючи):

```bash
npm run db:push
npm run seed-content
```

Кожна мовна секція форми (UA/EN/ET) — окремий згорнутий `<details>` в
одній формі, як і в "Власних полях". Фото (обкладинки новин, лого
портфоліо) зберігаються в `data/content-images/` і віддаються публічно
(без авторизації — це маркетингові картинки) через
`/api/content-images/[file].ts`.

## SEO

- `og:image`/`twitter:image` — `public/og-image.png`, згенерований з

  кольорів бренду в `global.css`).
- JSON-LD `Organization` на кожній сторінці (`BaseLayout.astro`).
- Кожен пост новин має опційні SEO-поля (заголовок/опис) окремо на

## Перед публікацією

- Заповнити email/Telegram на `/app/admin/settings/site` — замінить
  плейсхолдери `[EMAIL]`/`[TELEGRAM]` на сторінці "Контакти" (усіма
  мовами) без правок коду.
- Дати естонський текст (особливо `about.p2` в `ui.ts`) на звірку
  носію мови перед показом реальним клієнтам в Естонії.
- Створити свій адмін-акаунт на проді (`npm run create-admin`) з
  надійним паролем — приклад вище використовує тестовий.
- Регулярно бекапити `data/app.db`, `data/uploads/`,
  `data/project-files/` і `data/content-images/` (клієнти, тікети,
  прикріплені файли, фото/лого контенту), а також `data/.encryption-key`
  (або задане в `.env` значення `CREDENTIALS_ENCRYPTION_KEY`) — без
  нього збережені в проектах доступи (паролі хостингу тощо) розшифрувати
  не вдасться.
- Задати SMTP на `/app/admin/settings/site` (хост/порт/логін/пароль/From) —
  пароль зберігається зашифрованим (`smtp.pass` в `site_settings`, той
  самий `src/lib/crypto.ts`, що й у сховищі доступів проекту), не
  відкритим текстом. `SMTP_*` в `.env` лишається робочим фолбеком, якщо
  зручніше налаштувати на рівні сервера, а не через адмінку — налаштування
  з UI має пріоритет, якщо задано обидва. Кнопка "Надіслати тестовий
  лист" реально шле лист і показує справжню помилку (нев._адреса,
  неправильний пароль тощо), а не просто "чи заповнені поля".

## Kursor — власний рушій системи

Сайт, кабінет і CRM працюють на **Kursor** — власній розробці, а не на
WordPress чи готовій SaaS. Назва й іконка (`src/components/KursorMark.astro`)
навмисно побудовані на тому самому мотиві "курсора", що й в основному
лого (`Logo.astro`) — не новий візуальний стиль поруч, а той самий
акцент, названий і оформлений в окрему марку. Секція на головній
(`KursorSection.astro`, підключена на всіх трьох мовних версіях
`/`, `/en`, `/et`) показує можливості рушія (CRM, тікет-система,
CMS, API, шифрування доступів, мультимовність) — переклади в
`src/i18n/ui.ts` під ключами `home.kursor.*`.

## Деплой на власний VPS (nginx + systemd)

```bash
npm run build
rsync -avz --delete --exclude data/ . user@server:/var/www/intech.org.ua/
# на сервері (перший деплой):
npm ci --omit=dev
npm run db:push          # створити базу
npm run seed-content     # перенести контент, що жив у коді, в базу
npm run create-admin -- --email you@intech.org.ua --name "..." --password "..."
```

- `deploy/nginx.conf.example` — реверс-проксі на Node-процес
  (`127.0.0.1:4321` за замовчуванням) для основного домену й
  `admin.intech.org.ua`, з кешуванням статичних `/_astro/` асетів.
- `deploy/intech.service.example` — systemd unit, щоб `node
  dist/server/entry.mjs` автоматично піднімався після рестарту/збою
  (`systemctl enable --now intech`).
- Сертифікат на всі три імені: `certbot --nginx -d intech.org.ua -d
  www.intech.org.ua -d admin.intech.org.ua`.
- **PDF (Puppeteer)** — генерація квитанцій/рахунків/договорів у PDF
  тягне за собою headless Chromium (`puppeteer`, звичайна залежність,
  не dev). `npm ci --omit=dev` все одно її поставить; на VPS має бути
  достатньо RAM для Chromium (орієнтовно +200-300 МБ на короткочасний
  процес рендеру одного документа) — на мінімальних 512 МБ дропletах
  може знадобитись swap.

## Бренд

Кольори, шрифти й іконка живуть у `src/styles/global.css`
(`--ink`, `--accent`, `--accent-secondary`, …) та в `src/components/Logo.astro`.
Бренд-палітра — зелений/білий (`--accent`/`--accent-secondary`; було
жовто-синє "прапорове" поєднання, перефарбовано на прохання клієнта —
`--accent-secondary` це та сама роль, що мав старий `--flag-blue`:
білий у темній темі, темний нейтральний у світлій, той самий принцип
"фліпу", що й у `--ink`/`--paper`). Той самий знак, що затверджений в
окремому лого-канвасі: жирний wordmark "intech" з двоколірним курсором
і квадратна іконка з тим самим елементом для фавікону.

### Світла/темна тема

Темна — бренд-дефолт (як і раніше), світла — вмикається перемикачем у
хедері й у кабінеті (`ThemeToggle.astro`), зберігається в
`localStorage`. Значення токенів для обох тем — у `global.css`
(`:root` — темна, `:root[data-theme='light']` — світла); є окремий
токен `--on-accent` для тексту на жовтій кнопці, який навмисно НЕ
змінюється між темами (інакше кнопка стане нечитабельною в один з
двох режимів). Блокуючий inline-скрипт у `<head>` (BaseLayout,
AppLayout, login) виставляє тему до першого рендеру, щоб не було
"спалаху" не тієї теми.

### Новини та партнери

`src/data/news.ts` — короткі новини (uk/en/et), показуються на
головній (3 останні) і на `/news`. `src/data/partners.ts` — зараз
порожній навмисно: секція партнерів на головній не рендериться, поки
масив пустий (жодного "порожнього" блоку на живому сайті). Додати
партнера — один об'єкт `{name, url, logo}`, лого — за тим самим
принципом, що й портфоліо (`/public/portfolio-logos`).

Кожен пост має обкладинку (`image`, файл у `/public`) або, якщо фото
ще нема, згенерований бренд-плейсхолдер за іконкою (`icon: 'launch' |
'globe' | ...` — див. `NewsCover.astro`; додати новий варіант —
дописати SVG-path у словник `icons` там же). На сторінці поста є
кнопка "Поділитись" (Web Share API з фолбеком на копіювання
посилання) і коментарі: **з модерацією** — новий коментар публічно НЕ
видно, поки ви не натиснете "Схвалити" на `/app/admin/comments`.
Через це сторінки постів (`/news/[slug]`) більше не статичні —
`prerender` там прибрано, бо статична сторінка не показала б нові
схвалені коментарі без повного передеплою; список `/news` лишився
статичним (він коментарів не показує).
